[Normal] Multi-tenant Fitness & Wellness SaaS Platform
[Normal] Architecture: Master/Control Database + One Dedicated PostgreSQL Database Per Tenant
[Normal] File Storage: Zata.ai S3-compatible object storage on NeevCloud
[Normal] Status: Finalized design baseline for Phase 1 implementation
[Heading 1] 1. Final Architecture Decisions
[List Bullet] One Master/Control DB manages the SaaS control plane, platform IAM, tenant registry, SaaS plans, subscription billing, resource usage, marketplace, domains, branding, database routing and platform audit.
[List Bullet] Every tenant has its own dedicated PostgreSQL database. The database may be PLATFORM_MANAGED or CUSTOMER_MANAGED (AWS, NeevCloud, another cloud, or customer datacenter).
[List Bullet] The platform team creates and controls Tenant -> Organization -> optional Company Entity -> Location -> Branch. Tenant Org Admin manages departments, users, roles, permission matrices and role assignments inside that structure.
[List Bullet] Both platform users and tenant users have Department -> Role -> Module visibility -> Submodule visibility -> Action permission controls.
[List Bullet] Tenant product modules are assigned at tenant level and may be ALL_BRANCHES or SELECTED_BRANCHES. Super Admin controls branch-level module availability.
[List Bullet] Tenant/organization/location/branch deactivation is non-destructive. It blocks access/operations but does not automatically deactivate users or erase historical relationships.
[List Bullet] All tenant/end-user files are stored as objects in Zata.ai S3-compatible storage. PostgreSQL stores metadata, ownership, classification and object keys only.
[List Bullet] Legacy data is migrated through a staging/transform/reconciliation process and standardized into the new schema while preserving legacy IDs and traceability.
[Heading 1] 2. High-Level Hierarchy
[List Bullet] MASTER DB -> Tenant -> Dedicated Tenant DB
[List Bullet] Tenant DB -> Organization -> Company Entity [optional] -> Location -> Branch
[List Bullet] Tenant Org Admin -> Department -> Role -> Permission Set/Scope -> Module -> Submodule -> Action
[List Bullet] Platform Staff -> Platform Department -> Platform Role -> Platform Module -> Platform Submodule -> Action
[Heading 1] 3. Ownership and Administration Model

[Heading 1] 5. Module Assignment and Branch Applicability
[List Bullet] When a tenant is onboarded, assigned modules default to availability_mode = ALL_BRANCHES unless Super Admin chooses SELECTED_BRANCHES.
[List Bullet] For ALL_BRANCHES, every existing and future active branch inherits the module without creating a branch_modules row.
[List Bullet] For SELECTED_BRANCHES, Super Admin explicitly maps enabled branches in branch_modules. A new branch does not receive that module until selected.
[List Bullet] Tenant Org Admin can configure role visibility/permissions only for modules actually entitled to the tenant and available at the relevant branch.
[Heading 1] 6. Storage and Resource Metering
[List Bullet] Tenant DB storage: measured from PostgreSQL for platform-managed tenant databases.
[List Bullet] File/media storage: actual objects are stored in Zata.ai S3 with tenant-namespaced object keys; S3/provider metrics are the authoritative storage measure.
[List Bullet] Resource metrics can also track active members, branch count, trainer accounts, AI voice minutes, API calls, backup storage and other plan quotas.
[List Bullet] Customer-managed resources may be observed for health/visibility but can be marked is_platform_billable = FALSE.

[Heading 1] 9. Dedicated Tenant Database Schema
[Body Text] Every tenant receives the same standardized tenant schema. This design contains 28 runtime/support tables including the recommended legacy mapping table.
[Heading 3] 1. organizations
[Body Text] Business organization inside the tenant DB. Created/managed by the platform team.
[Normal] Design note: Normal onboarding creates one organization per tenant. Tenant Org Admin can view but cannot structurally create/deactivate it.
[Heading 3] 2. company_entities
[Body Text] Optional legal/company entities under the organization. Created/managed by the platform team.
[Heading 3] 3. locations
[Body Text] Geographical/business areas such as Goregaon West. Created/managed by the platform team.
[Heading 3] 4. branches
[Body Text] Actual operational gyms/studios/centres. Created/managed by the platform team.
[Normal] Design note: Branch deactivation blocks new branch operations but does not deactivate users, delete history, cancel memberships or reset future cross-branch/passport balances.
[Heading 3] 5. users
[Body Text] Tenant-side people/accounts: staff, members, online clients, guests and trials.
[Normal] Design note: Tenant login is allowed only when tenant.status=ACTIVE and user.status=ACTIVE; existing API sessions are also tenant-gated centrally.
[Heading 3] 6. user_branches
[Body Text] Historical/operational user-to-branch associations.
[Normal] Design note: UNIQUE(user_id, branch_id, relationship_type). Branch closure never deletes this history.
[Heading 3] 7. departments
[Body Text] Tenant-created departments within the organization.
[Heading 3] 8. user_departments
[Body Text] Many-to-many user membership in tenant departments.
[Normal] Design note: UNIQUE(user_id, department_id).
[Heading 3] 9. module_catalog
[Body Text] Tenant-local synchronized copy of enabled product module catalogue.
[Heading 3] 10. submodule_catalog
[Body Text] Tenant-local synchronized product submodule catalogue.
[Heading 3] 11. permissions
[Body Text] Tenant-local synchronized action permission catalogue.
[Heading 3] 12. roles
[Body Text] Tenant-created roles, usually under a department.
[Heading 3] 13. role_permission_sets
[Body Text] Defines a role permission matrix at Organization, Company Entity, Location or Branch scope, with inheritance.
[Normal] Design note: Scope validation must ensure only the matching structural FK is populated. Inheritance: organization default -> company entity/location -> branch override.
[Heading 3] 14. role_module_access
[Body Text] Role permission-set module visibility.
[Normal] Design note: UNIQUE(permission_set_id, module_id).
[Heading 3] 15. role_submodule_access
[Body Text] Role permission-set submodule visibility.
[Normal] Design note: UNIQUE(permission_set_id, submodule_id).
[Heading 3] 16. role_permission_set_items
[Body Text] Action permissions allowed/denied within a permission set.
[Normal] Design note: UNIQUE(permission_set_id, permission_id). Permission matrix = Department -> Role -> Module -> Submodule -> Action.
[Heading 3] 17. role_assignments
[Body Text] Assigns a tenant role to a user at a structural scope.
[Normal] Design note: Org Admin uses ORGANIZATION scope and can see the full organization hierarchy subject to permissions.
[Heading 3] 18. branch_modules
[Body Text] Super-Admin-controlled branch-level module applicability when tenant_modules.availability_mode=SELECTED_BRANCHES.
[Normal] Design note: UNIQUE(branch_id, module_id). For ALL_BRANCHES modules, an explicit row is not required; availability is inherited. For SELECTED_BRANCHES, only explicitly enabled rows are available.
[Heading 3] 19. organization_settings
[Body Text] Organization-level business defaults.
[Normal] Design note: Configuration inheritance: platform defaults -> organization settings -> branch override.
[Heading 3] 20. branch_settings
[Body Text] Branch-specific overrides of organization settings.
[Heading 3] 21. notification_templates
[Body Text] Tenant-owned notification templates with optional branch override.
[Heading 3] 22. processing_purposes
[Body Text] DPDP/privacy processing-purpose catalogue.
[Normal] Design note: Examples: CORE_SERVICE, MARKETING_EMAIL, MARKETING_WHATSAPP, AI_COACHING, NUTRITION_ANALYSIS, WEARABLE_PROCESSING, COMPUTER_VISION_ANALYSIS.
[Heading 3] 23. consent_records
[Body Text] Historical consent ledger; do not overwrite previous evidence.
[Heading 3] 24. privacy_requests
[Body Text] Data-principal/privacy rights workflow.
[Heading 3] 25. audit_events
[Body Text] Append-only tenant audit ledger.
[Normal] Design note: Never log passwords, OTPs, JWTs, authorization headers, session cookies, secret keys or full sensitive payment data.
[Heading 3] 26. files
[Body Text] Metadata registry for all tenant/end-user files. Actual binaries are stored in the Zata.ai S3-compatible bucket on NeevCloud.
[Normal] Design note: Store metadata only in PostgreSQL. Use short-lived signed URLs after authorization. Namespace object keys by tenant. Actual S3/provider metrics are authoritative for storage billing; files.file_size supports application-level reconciliation.
[Heading 3] 27. integrations
[Body Text] Tenant-side configuration of enabled external integrations.
[Normal] Design note: UNIQUE(integration_type, provider). Examples: Razorpay, ICICI, TeleCMI, Gupshup, SES, Meta, Timewatch.
[Heading 3] 28. legacy_entity_map
[Body Text] Recommended migration traceability map from legacy records to standardized new entities.
[Normal] Design note: UNIQUE(source_system, legacy_entity_type, legacy_entity_id). Recommended as a migration-support table/schema; preserves legacy traceability without carrying the legacy schema forward.
[Heading 3] 29. branch_working_hours
[Body Text] Per-branch weekly operating schedule with day-of-week open/close times.
[Heading 3] 30. branch_operating_exceptions
[Body Text] Per-branch calendar date operating exceptions, closures, or modified holiday hours.

[List Bullet] 14. Activate tenant after validation.

[Heading 1] 14. Implementation Guardrails
[List Bullet] Use UUID primary keys for new entities; maintain proper foreign keys within each database.
[List Bullet] Use RESTRICT/PROTECT for structural and historical relationships; avoid accidental destructive CASCADE deletes.
[List Bullet] Do not trust tenant_id from the frontend to choose a database. Resolve tenant from trusted domain/context and Master DB routing.
[List Bullet] Keep Master DB and Tenant DB models explicitly separated in Django database routing.
[List Bullet] Keep secret values in a secrets manager/Vault. Store only secret_reference in PostgreSQL.
[List Bullet] Use Redis/Celery for asynchronous usage collection, database health checks, notifications, provisioning and catalogue synchronization.
[List Bullet] Generate signed object URLs only after authorization. Do not expose permanent public Zata S3 URLs for restricted files.
[List Bullet] Keep platform audit and tenant audit append-only at application level and redact sensitive data.
[List Bullet] Apply database schema version checks before serving a tenant whose database is customer-managed.
[List Bullet] Treat UI visibility as presentation only; every API must independently enforce entitlement, scope and action permission.
